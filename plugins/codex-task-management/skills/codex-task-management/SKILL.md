# Codex 任务管理

任务状态、依赖和派工记录以 Taskboard（SQLite + `taskctl`）为唯一数据源；项目内不再维护 INDEX 或任务卡。本 Skill 统一对话职责、派工、接单与验收规则；项目 AGENTS.md 只补充项目事实、业务边界和指定入口。

## 项目与 issue 结构

- 开始前先跑 `taskctl context current` 确认当前会话映射的 project 与 workspacePath；映射错误用 `taskctl project map` 修正后再操作。
- 一个项目一个 project；同一模块批次建一个 parent issue，各模块任务为其 children。层级只用于组织任务；对话职责由用户要求和下节规则确定。
- 依赖用 `blocked_by` 记录，并在任务书里写明原因：`functional`（功能上依赖上游产物）或 `serialization`（共享资源必须串行）。没有真实依赖的 issue 保持平行，不人为串联。
- 跨目录协作（如项目关联的知识库目录）默认只读。issue 需要修改辅助目录时，任务书必须显式列出该目录的文件归属；否则为辅助目录单独建 issue，不搭车修改。

## 对话职责

- 用户指定主控时，将主控 thread ID 和职责记入批次 parent issue。主控负责规划、派工、依赖、审查和串行集成；执行卡由各自独立、可见且可继续交互的 Codex 对话自行接单和交付。主控不代领执行卡，不因执行者暂停而自动接管候选修改；可维护批次规划、派工记录及用户明确交给主控的公共治理规则。
- 执行卡包括已派出、需要持续维护产物的调查、方案和代码任务。一个执行对话只绑定一张未完成执行卡；待审或受阻仍算未完成。普通需求讨论、只读问答和辅助评审不因此强制建卡。未指定主控的单项任务可由当前对话接单，不强制增加协调层。
- 临时子代理和 CLI 进程可以辅助已有执行对话，成果与写入权仍由接单对话负责。临时进程、trace ID、后台子代理或工作区存在，均不能替代独立任务身份；创建新任务遵守用户授权及宿主工具约定。

## 派工与执行

1. 规划：在 Taskboard 建 parent/children issue，写清依赖与原因。按 [任务书与回执](references/task-protocol.md) 写入目标、文件归属、公共文件及共享资源负责人、基线、输入合同和 `## required_checks`。
2. 派工：逐张检查资格（todo、无 threadBinding、blocked_by 全部 done、项目 WIP 未满）。按已获授权创建或复用该卡的独立执行对话，首条消息携带任务书、主控身份、规则入口、基线和自行 claim 的要求。看板和标签不会自动启动任务；不合格卡保留真实原因。创建返回临时 ID 时只记“创建中”，取得正式 thread ID 后再核对接单。
3. 接单：执行对话先核对自身不是本批主控，且没有其他未完成执行卡，再运行 `scripts/claim.sh <ISSUE_ID>`。脚本通过后 issue 转 in_progress、绑定该对话，并创建或复用独立 worktree（`<主工作区>-<issue小写>`，分支 `codex/<issue小写>-<标题slug>`）。同卡恢复先核状态：in_progress 才能继续写；in_review 保持冻结，需修改先按退回流程处理；已结束卡不重入。校验或脚本失败只停相关动作，不手工改状态、绑定或线程环境绕过，也不由主控代做。
4. 开发：接单对话只在 claim.sh 创建的 worktree 内改代码（`git -C <worktree路径>` 或 cd），bootstrap 项目规则后实现；每个 worktree 一个 writer，主工作区保持主分支不动。
5. 交付：完成约定产物、自查、独立评审及授权范围内的修正复核后，由接单线程自己执行 `taskctl issue move <ID> --status in_review --thread-id <本线程ID>`，comment 交付回执；writer 停止修改候选。不要跨对话代跑：跨线程 move 会清掉接单绑定，land.sh 将无法定位主工作区。
6. 退回与取消：候选需要修改时先退回 in_progress，由原对话在批准范围内修复、复验并复核最终版本；涉及新增范围或权限才请求对应确认。需求取消转 canceled 并注明原因。
7. 验收：在 issue 对话交付具体结果供用户验收；合并必须取得用户明确批准。候选冻结或待合并仅暂停相关动作，独立且已授权的调查继续。
8. 合并：用户批准后执行 `scripts/land.sh <ISSUE_ID> "<批准说明>"`。脚本自动 rebase、逐条执行 required_checks、`merge --no-ff` 回主分支、写 landed 回执并转 done。
9. 清理：删除 worktree 与分支、归档对话，按"复盘与清理"沉淀。

### 派工完成标准

主控逐卡读回正式 thread ID 与可访问任务、执行对话自己的接单回执、实际工作树路径/分支/HEAD、文件及共享资源归属，以及该对话开始处理任务的返回记录；全部对应后才报告“已启动”。记录格式见 [任务书与回执](references/task-protocol.md)。只有创建请求、工作树或接单成功时，分别报告实际进度，不提前合称派工完成。

`threadBinding.workspacePath` 是项目主目录；实际写入目标以 `developmentContext.path` 和 `.branch` 为准，并核对 Git 结果。App 初始目录可能另有工作树，执行命令必须明确指向接单登记的目录，不能把界面目录当作已完成代码隔离的证据。共享浏览器、设备、端口、数据库及外部账号另行指定唯一负责人或串行使用。

重新派工时，先确认旧执行者停止写入，保留候选和最后检查点，再按接单条件解除旧绑定，由新对话自行 claim 并读回。条件未满足时可明确安排只读交接，原状态和写入归属保持可追溯；不为转移任务伪造 done、退回或取消。

## 门禁的三层

- 脚本闸机：claim.sh / land.sh 把状态机校验（todo 才能接单、依赖全 done、WIP 上限、worktree 自动创建与写回、分支一致性、in_review 才能合并）固化进程序入口，不靠各对话自觉遵守约定。
- 原生约束：`--if-version` 乐观锁防并发覆盖单条更新；SQLite 单文件状态源天然排除双写。两者都防不了旧会话断线恢复后拿旧快照交作业，所以接单必须重新走 claim.sh 换新绑定，旧回执随绑定失效。
- 执行约定：当前 claim.sh 尚未自动检查主控身份、同线程持卡数、对话可见性和恢复状态；上述检查由执行者及主控落实。直接 `issue move` 也能绕过脚本，因此文档更新不代表硬限制已实现。后续若增加自动拦截，应在 Taskboard 绑定入口统一校验并由 claim 调用，分别验证主控接单拒绝、同线程第二卡拒绝、独立线程接单允许、冻结卡不可恢复写入。

## 硬约定

- WIP 上限：每项目同时 in_progress ≤ 2、in_review ≤ 2。claim.sh 在接单时执行准入检查并按项目加锁串行；交付转 in_review 不另设闸，超出部分由下一次接单的准入检查拦截。
- Taskboard SQLite 是唯一状态源。备份用文件级 copy；不同时编辑两个副本，恢复前先停写。
- 合并只走 land.sh，且必须在用户批准后；`--no-ff` 保留模块边界，landed_sha 写回 issue comment。
- 候选冻结：转 in_review 后 writer 不再改候选；要改先退回 in_progress。
- 验收分级：unit / snapshot / sandbox / live，按任务书声明的等级收证据；unit 通过不冒充 live 验证。

## 保留规则

- 独立评审：交付前由独立只读评审按交付对象先检查正确性，再查复杂度，结论覆盖最终版本。调查报告可以交付已查明的事实与缺口；依赖未验证关键合同的实施方案不能因此通过。
- 修正轮次仅作诊断记录，不是配额；同一阻断连续两轮未解先复核根因，再凭可验证的新依据继续。
- 推进节奏：按适用 AGENTS.md 的目标与结束条件持续推进；阶段交付后，主控安排其余已授权任务，执行者继续本卡范围内的必要工作。纯调查按约定范围交付，不将后续恢复视为自动获批；继续推进不改变接单归属。
- 失败恢复：先判断代码、环境、依赖还是外部状态问题；无法确定安全下一步时走自愈诊断，不机械重试。
- 长任务等待：绑定实际进程或会话句柄，按 ≤60 秒间隔读进度；两次空探测且无文件活动才判线程损坏。

## Skill 加载验收

交付 Skill 形态时，核验运行时发现路径、内容指纹和按批准样本的实际调用结果；文件存在不等于加载成功。项目 Skill 合入主分支即完成持久化，安装缓存不作修改入口。

## 复盘与清理

完成后提炼可复用经验回写本 Skill 或项目规则，无沉淀价值就不新增文件。清理 worktree、分支和一次性脚本；issue 保留在 board 上作为历史，不删除。
