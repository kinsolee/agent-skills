# Codex 任务管理

通用任务协作规则在本 Skill 维护；项目 AGENTS.md 只补充项目事实、业务边界和指定入口。项目计划与当前状态留在项目内，不复制到本 Skill。使用现有 Codex 任务能力，不另建调度、消息、日志或任务历史系统。

## 入口与责任

- 先读项目规则、权威索引和自身任务卡，再核对实际运行者、人工等待状态、主机、绝对目录、分支、HEAD、未提交差异及产物。恢复聊天不能替代当前状态核验；新任务不默认继承旧聊天。派工、接单和恢复都核对实际 Skill 路径与内容指纹；跨主机缺失或版本不符时只暂停受影响工作，不静默沿用旧副本或复制密钥。
- 项目指定一个主控和一个权威索引，默认用保存项目的集成工作区与 `docs/tasks/INDEX.md`；下文以 `main` 指集成分支，项目明确约定优先。主控负责范围、依赖、派工、集成、审查和最终验收；模块自主细化已批准范围。切换主控前停止旧主控派工和索引写入。
- 小步骤留在当前任务。只有可独立分配、交付和验收的工作才拆模块；未经用户明确要求不创建用户侧独立任务，短期独立探索和评审可使用子 Agent。不重复启动已有运行者，不与模块同时修改其负责文件。
- 派工、建卡或回传时读取 [任务书与回执](references/task-protocol.md)。创建流程生成的 ID、主机和路径在返回后核验补齐，不能猜测。用户决定目标与授权；子任务继承父任务的有效范围。仅实质改变目标、验收标准、真实对外合同或外部操作边界时核对新增授权，不把内部实现细化当作范围扩大。

## 活跃记录与执行基线

- 未完成工作只维护权威索引和每个模块工作树内的一张任务卡，默认 `docs/tasks/<任务标识>.md`。索引仅主控写，保存定位、依赖、阶段、修正次数和待决策入口；卡仅对应 writer 写，保存批准范围、检查点、证据和下一步，不复制完整聊天或日志。工作树复制出的索引不具权威性。
- 在方案批准、有意义的阶段结果、阻塞、交接及本轮结束前更新必要记录，不为每条命令写报告。批准须能定位到具体范围和版本；换对话不改变任务身份、授权或历史计数。
- 派工记录批准的 main 基线及规则、合同的实际版本；未提交文件还需可读取原件与内容指纹。main 更新不会自动同步到其他工作树，HEAD 相同也不证明未提交内容相同。变化只暂停受影响工作，由主控协调重读和安全同步，保护未提交成果。
- 主控到索引指定主机与绝对路径读取真实任务卡、差异和产物；跨节点取不到原产物就标记证据待核验，不凭摘要验收。落盘不是远端备份；同步前核验目标节点的 Skill、运行时、权限和凭据依赖。

### 依赖隔离与恢复

- 缺失的外部合同、额度或运行时能力只暂停直接依赖它的外部动作；不暂停已获授权且不依赖该能力的本地实现、测试、评审、证据整理或补丁准备。任务卡须分别列出“可继续的本地工作”和“被阻塞的外部条目”，不得把局部缺口升级为整项任务阻塞。
- 恢复或重启任务时，先读取最近有效检查点；若主控身份、Skill 指纹、目标范围、HEAD、工作树状态和外部前置均未变化，只复核变化项，不重复整套启动审计。任何变化都要记录失效范围和新的检查点。
- 重启模块不得默认丢弃旧工作树的未提交成果。新 worktree 建立后，唯一 writer 接手前必须从旧工作树生成包含 tracked、untracked 和 ignored 项的完整清单（例如 `git status --ignored`）、差异和内容指纹，逐项迁移并复核；目标已有同路径或内容冲突时先停下、保留两份并标为待核验，禁止覆盖。无法迁移的文件要保留原工作树，不得以 main 的 HEAD 代替。

## 正常推进与评审

- 独立代码交付使用独立 `codex/` 分支和 worktree，每个工作树同一时间一个 writer；小步骤共用工作树。公共合同、重叠文件和共享配置明确负责人。worktree 只隔离代码，设备、会话、schema 及危险外部副作用按冲突资源串行；只读或合同明确允许并行的操作无需全局串行。
- 模块先核对实现、真实合同和必要外部事实，再形成方案；缺失合同只暂停依赖该合同的方案条目，独立本地方案和实现准备可继续。由同一名独立只读评审者先检查架构与正确性，通过后检查过度设计；项目指定评审 Skill 时按其顺序执行，否则使用现有独立评审能力，不自动安装依赖。用户已要求实施且方案在授权目标内时，两项评审无阻断即可编码；只有用户明确保留的方案决策才等待人工。用户只要求研究或方案时，不自动进入实现；普通小改动不因此升级为模块方案流程。
- 设计、测试或调试中发现问题时，模块必须先分析根因和影响，再在已授权范围内提出并实施最小修正；不能只报告“发现问题”或把下一步推回主控。若修正会改变目标、对外合同、真实写入或费用，才暂停并请求相应决策。
- 仅直接阻断当前验收的 P0/P1 或关键证据缺口必须修复；P2/P3 不要求清零，复杂度检查不代替正确性审查。非阻断问题留待后续范围决定，不自动扩展任务。
- 已获实施授权的目标内，必要的本地修改、根因修复、防御性编码、测试、构建、只读核验、文档、独立审查、收取和约定验收正常推进，不逐步请求用户批准。新补丁、候选版本或计划 hash 只使受影响的旧证据失效，补验即可；不自动使原目标授权失效。
- `plan_fix_rounds`、`delivery_fix_rounds` 只用于追踪修正和诊断，不是自动推进配额；历史次数或计数未知不触发人工批准，也不清零掩盖历史。连续两轮仍有同一阻断时，先复核证据和根因、调整最小方案，再凭可验证的新依据继续；无安全下一步或准备重复失败动作时遵守既有自愈诊断规则，不机械重复或降低验收标准。
- 只询问必须由用户决定或缺少授权的变化：实质超出目标、对外合同、真实写入范围或费用预算，以及用户明确要求逐次批准的操作。已有批准在原模块对话生效，主控核对原文和范围后继续，不要求用户到主控重复确认；平台强制审批仍照常办理并说明来源。
- 实现后由一名独立代码审查者检查最终差异。审后改动仅补查受影响内容，结论必须覆盖最终版本，不反复重跑无关方案审查。纯说明文档做一致性、链接和差异检查；只补路径等元数据检查差异即可。AGENTS、Skill 或可执行配置改变行为时补验相关加载/执行，静态检查不冒充运行成功。

### 主动推进与失败恢复

- 已接单且有明确下一步、且候选未冻结或未交付的任务持续由当前 writer 推进；不能以“等待用户继续”、空泛的“方案已准备”或一次阶段回执结束目标。交付待验收或冻结后 writer 停止修改，等主控验收或收到解除冻结指令。每轮结束前要么完成下一个已授权动作，要么给出具体阻塞、最后检查点和可执行恢复动作。
- 长测试、构建或外部等待必须绑定实际进程、session、job 或工具句柄，并按不超过 60 秒的间隔读取进度；无输出不等于完成或阻塞。超过预期时先检查句柄是否仍存活、进程状态、日志和资源占用，再决定继续、限时终止或修复，不得无界等待。
- 命令失败、测试失败或调试异常不自动结束任务。先判断是代码、环境、依赖、权限、外部状态还是工具调用问题；可确定安全且有证据支持的局部修复或替代检查可直接执行。无法确定安全下一步或准备重复失败动作时，立即调用适用的自愈诊断，再按其建议继续；不要机械重试。任务卡只记录最小脱敏错误摘要和复现命令，原始输出仅在受控临时位置保存并排除凭据，收尾时删除。
- 阶段性结果若暴露直接阻断当前验收或已授权范围内的设计缺口，必须回到受影响的调用链和验收条目，修正根因并补查受影响证据；非阻断的 P2/P3 只记录待办并交主控决定，不自动扩大范围。不能把“测试脚本很久”“某个回执为空”或“工具返回错误”直接当成业务失败，也不能用较窄的测试或历史摘要宣称目标完成。

## 冻结、验收与集成

1. 模块完成约定的合并前检查、独立审查及适用的部署/加载验证，冻结候选与证据。未提交候选须包含完整可审差异、新增文件及内容指纹。验收位置独立于开发位置；依赖 main 的部署、加载或业务回读列为合并后条目，需要环境而缺失时标待验证，确实无需该项才标不适用。
2. 技术验收默认由主控依据实际结果完成；仅用户明确要求或已约定必须由人判断的效果验收等待人工。需要时在原模块展示冻结版本、结果入口及待验条目，记录确认原文、时间、候选和编号。未通过则在既有范围内修复、重新冻结并补查受影响内容；有效确认不重复索取。
3. 模块使用原生 `send_message_to_thread` 向任务书中已核验的主控 ID/主机发送“交付待验收”回执，注明“约定检查已通过，待主控验收/集成”；人工验收或合并仅在适用时列状态。同一候选的同一结果只通知一次。交付回执不等于主控最终验收，不自行清理成果。
4. 主控读回原始证据、实际冻结候选、独立审查覆盖范围及适用的人工确认，核对最新 main 和提交、合并、推送各自授权；已有授权就继续，不另问是否收取或推进。唯一集成者按依赖逐个合并并回读 main，完成最小相关检查及约定的合并后部署/加载、业务样本与精确读回。分别说明代码验收、main 集成、部署/加载、真实业务验收，未完成或不适用须明确。
5. 回传交付后 writer 停止改候选。需要修改时，由主控确认未在集成并暂停收取，再由唯一 writer 解除冻结；这是 Agent 间并发协调，不转为用户审批。受影响的旧审查和验收失效，不边改边合并。合并冲突或行为变化须补查，影响已明确约定的人工判断内容才回原模块补验；其余由主控补验。依赖 main 的人工验收也在原模块完成。
6. 全部必要验收通过后标记“验收通过，待收尾”，结束该模块的业务迭代，只继续下节复盘和清理。缺必要验收或 Git 授权时保留成果和待办，不把局部通过报成全部完成。

进度查询使用原生读取/等待接口，不发“继续”消息代替查询。原生工具缺失只阻塞相应动作；本轮结束不等于开启持续监控，需要后台跟进时依据用户授权使用原生自动化。外部读写、模型调用及 Git 操作按已有目标、范围、预算和前置状态执行；已授权验收及其必要读回不逐次另批。新写入目标、数据传输目的地、费用或明确次数预算变化须核对新增授权，不能用“验收”扩大权限。结果不明先精确回读，禁止盲重试；用户明确逐次批准和平台审批要求保持。

## Skill 交付时的加载验收

仅在交付本身需要 Skill 时适用，不要求每个模块包装为 Skill。用户指定安装范围优先；项目模块候选默认放在其工作树的 `.agents/skills/<skill-name>/SKILL.md`，资源一起冻结且受 Git 跟踪，复用已有实现而不搬迁代码。候选验证不先覆盖 main 或用户全局版本；用户级安装需对应需求与授权。

实际核验运行时发现、选中的目录、内容指纹和按批准样本执行的调用结果。读取文件、目录存在或技能名称可见只证明部分状态，不证明执行；同名 Skill 不假定覆盖，新版本不能用旧上下文冒充。未发现更新先核验加载状态并保存检查点，再按宿主机制处理。

主控合入 main 即完成项目 Skill 的版本持久化，无需再复制一套。清理工作树前核验 main 中的引用、依赖、实际发现与调用，不能遗留指向待删除工作树的路径；验证不扩大业务权限。

## 完成后的复盘与清理

1. 在原模块对话简要提炼复用经验，优先更新现有 Skill、项目规则或适用的全局规则；没有明确复用价值就不新增文件，不另写复盘报告。更新仍须符合现有授权，项目专属事实不写入全局。
2. 主控就地更新 README 对应功能的已实现能力、使用入口和实际限制，不追加任务流水或长日志。未完成事项先移交必要事实、依赖、授权及适用历史计数，不得因删卡丢失历史次数和诊断结论。
3. 核对精确路径、引用与恢复方式后，删除已完成任务卡、过程计划/评审、一次性脚本/日志/快照及无用恢复物，修正失效链接。代码、必要测试、现行合同、运行恢复和未完成工作仍依赖的资料保留；旧文档独有的有效结论先提炼。清理专用短期副本读回后移除，不新建永久任务归档目录或 ZIP，不重写 Git 历史、不导出聊天另存一份。
4. 核验实现、README 和必要沉淀已按授权持久化且无活动 writer，再清理专属工作树及已集成分支，通过原生归档工具归档模块对话并读回。未验收或未安全保存的工作树保持置顶，不提前归档清理；已完成模块不接新业务，主控继续协调。收取、清理与归档在同轮完成，不等用户另行提醒；必要授权或能力缺失时保持待收尾并说明具体缺项。

后续调整通用协作规则只修改本 Skill 及相关模板；项目只维护自己的边界和入口。验收分别说明静态结构、实际发现/调用和真实模块协作流程，不能互相替代。

本 Skill 的维护源码位于 [kinsolee/agent-skills](https://github.com/kinsolee/agent-skills/tree/main/plugins/codex-task-management)。修改本 Skill 或引用资源时，先读取源码仓库根目录的 `AGENTS.md`，按该仓库约定验证、提交和推送；安装缓存不作为源码修改入口。
